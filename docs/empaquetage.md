## macOS : signature et notarisation

**macOS signing + notarization work (2026-09-15, #75 / PR #105).** `npm run release:mac` (or `release:mac-arm` / `release:mac-intel`) signs with the Developer ID certificate in the keychain and notarizes through the `cliodeck-notary` notarytool profile; `build:mac*` signs but never notarizes. Config is `mac.notarize: true` — **not** `{ teamId }` (electron-builder passes it alongside keychain/API-key credentials and `@electron/notarize` 2.2.1 rejects the mix) and never `APPLE_ID` in the environment (`true` + `APPLE_ID` falls back to the closed `altool`). `mac.target` lists x64 **and** arm64, so `build:mac-arm` builds both. The Intel app built on Apple Silicon needs llama.cpp's x64 engine package, which `npm ci` only installs for the host arch: every `build:mac*` runs `npm run fetch:llama-mac` (lock-verified tarballs, no tree rewrite) — without it the rc.6-beta.2 Intel DMG shipped with no embedded model (#128). Check bundled binaries' arch with `file` (`docs/macos-notarization.md`). Signing timestamps every file against `timestamp.apple.com`: a network blip fails the build, rerun. Procedure and machine prerequisites (G2 intermediate CA, Xcode licence): [`docs/macos-notarization.md`](docs/macos-notarization.md). CI signing is not wired; the DMGs published for `v1.0.0-rc.4` are unsigned. **Under electron-builder 26 (#147) the contract is unchanged, and exercised on 2026-10-05**: `release:mac` signed, notarized and stapled both apps (arm64 and Intel), Gatekeeper answers « Notarized Developer ID ». `{ teamId }` is now rejected by the schema. Signing goes through `scripts/mac-sign.cjs` — without it `codesign` does not find the certificate (see the electron-builder 26 entry below).

## Electron 43 : installation

- **`better-sqlite3` est compilé depuis les sources** par le `postinstall` : aucun binaire précompilé n'existe sur npm pour l'ABI d'Electron 43 (la 12.12.0 qui en fournit n'a été publiée que sur GitHub ; la dernière 12.x de npm est la 12.11.1). Passer à Electron ≥ 44 demande `better-sqlite3` 13 (réécriture N-API), à faire à part.
- **Le paquet `electron` ne télécharge plus son binaire à l'installation** (Electron 42) : le `postinstall` appelle `install-electron` pour que `npm install` laisse comme avant une app lançable.

## electron-builder 26

**electron-builder 26 depuis le 2026-10-05 (#147) — ce qui ne se devine pas.** La 24 produisait des AppImage qui chargeaient des bibliothèques depuis le dossier courant (GHSA-7g7r-gx96-252g) ; corrigé à partir de la 26.15.
  - **`rebuild:native`, `rebuild:x64`, `rebuild:arm64` et le `postinstall` appellent `electron-rebuild --force`, et non plus `electron-builder install-app-deps`.** La 26 délègue à `@electron/rebuild`, qui saute tout module portant son marqueur `build/Release/.forge-meta` — même si `npm rebuild better-sqlite3` a remplacé le binaire entre-temps. Résultat mesuré : `test:integration` laissait l'ABI Node en place en affichant « completed installing native dependencies », code de sortie 0, et l'app ne démarrait plus. `install-app-deps` n'a pas d'option pour forcer. Ne pas retirer `@electron/rebuild` des `devDependencies`, quoi qu'en dise l'avis d'electron-builder. `test:integration` contrôle désormais lui-même la restauration en ouvrant une base sous Electron.
  - **Après chaque montée d'Electron, `npm update node-abi`.** `@electron/rebuild` lit l'ABI dans la table de `node-abi` et **s'arrête** si la version d'Electron n'y figure pas (« Could not detect abi for version … ») — la 24 se rabattait sur une compilation. Sont alors cassés d'un coup `rebuild:native`, le `postinstall` et la restauration d'ABI de `test:integration`.
  - **Linux** : les clés du fichier `.desktop` vont sous `linux.desktop.entry` (à plat, la configuration est refusée). `executableArgs` vaut `[]` : `["%U"]` donnait `Exec=AppRun %U %U`, et l'absence de valeur ferait écrire `--no-sandbox` dans la ligne `Exec` de l'AppImage.
  - **Le lanceur de l'AppImage ajoute lui-même `--no-sandbox`** quand les espaces de noms utilisateur non privilégiés sont indisponibles (`unshare -Ur true` échoue : Ubuntu 24.04 par défaut). Ce n'est pas réglable. Avant, l'AppImage ne démarrait pas du tout sur ces systèmes ; maintenant elle démarre sans bac à sable Chromium, sans le dire. Le `.deb` n'est pas concerné (profil AppArmor et `chrome-sandbox` installés). **Décision (#151, 2026-10-05) : accepté, à condition de le dire.** `sandboxStatus` (`src/main/utils/sandbox-status.ts`) le détecte — sous Linux seulement, les tests e2e passant `--no-sandbox` partout — et `useSandboxWarning` affiche au démarrage un avertissement qui reste jusqu'à fermeture et renvoie au `.deb`. Vérifié dans l'app réelle en forçant la réponse IPC ; **jamais vu sur une vraie machine Linux**.
  - **La signature macOS passe par `scripts/mac-sign.cjs` (`mac.sign`) — ne pas le retirer sans vérifier.** La 26 prépare la signature avec l'empreinte SHA-1 du certificat, puis la remplace par son **nom** en appelant `codesign`, qui ne retrouve pas un nom accentué : « Developer ID Application: Frédéric Clavert (…): no identity found », certificat pourtant présent. Le crochet reçoit les options avant ce remplacement et signe avec elles. Corrigé en amont (electron-builder@56d2d746) mais dans aucune 26.x publiée, 26.17.0 comprise. **Un build signé ne se vérifie pas en signant** : mettre devant le `PATH` un faux `codesign` qui note ses arguments et réussit, lancer `electron-builder --mac --arm64 --dir`, et lire ce qui suit `--sign` — l'empreinte, pas le nom.
  - **Tester une app empaquetée non signée : toujours `--use-mock-keychain`.** Sans cela elle sollicite la vraie entrée « ClioDeck Safe Storage » du trousseau avec une signature inconnue, macOS demande confirmation, et le processus reste bloqué à « Initializing configManager » — `SIGTERM` ne l'arrête pas. Recette : `electron-builder --mac --arm64 --dir -c.mac.identity=null -c.directories.output=<ailleurs>`, puis `codesign --force --deep -s -` sur le `.app`, puis Playwright `_electron.launch({ executablePath, args: ['--use-mock-keychain', '--user-data-dir=…'] })`.
  - **Le contenu du paquet se compare, il ne se suppose pas.** La 26 range `node_modules` autrement dans `app.asar` (mêmes paquets, autres emplacements). `npx asar list` avant/après, par nom de paquet, a servi de contrôle.
  - Une cible Linux se construit depuis macOS avec `-c.npmRebuild=false` **uniquement pour lire** `AppRun` et le `.desktop` : les modules natifs qu'elle contient sont ceux de macOS.
